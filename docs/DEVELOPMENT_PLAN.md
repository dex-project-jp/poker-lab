# Poker Lab 開発計画・引き継ぎ台帳

更新日：2026-11-05（日本時間）
リポジトリ：https://github.com/dex-project-jp/poker-lab

## 運用の合意

ユーザーの「次の作業」を手動の開始合図とする。合図のたびに、最新のGitHubと目標を確認し、次の1工程を担当エージェントが判断して完了まで進める。定期実行・無人の継続開発・有償計算を予約したものではない。

通常の実装、回帰修正、テスト、精度検証、コミット・push・PR作成/更新、計画更新は都度の確認を求めない。大きな設計変更、破壊的な移行、費用が必要な外部計算/サービスは、具体的な案・利点・影響・必要費用を示して事前確認する。確認が必要な決定に依存しない調査や可逆的な準備は進めてよい。

ユーザーはiPhone中心で利用する。既存の段階式入力、最上部のポジション選択、169ハンド表、更新ボタン、PWA、30BB参考レンジを維持する。説明や操作を増やしすぎない。

## 最終目標

プリフロップからリバーまで、人数・位置・スタック・ベットサイズ・行動履歴・ボードに応じた正確なGTO頻度とEVを確認し、相手の戦略を仮定したエクスプロイト分析もできる実戦向けアプリ。最終的な公開・課金より先に、モデルと精度の裏付けを整える。

現状の10BB Fold/Jam/Call限定ゲームから、全状況対応までの進捗を根拠のない割合で示さない。モデル範囲・検証範囲・表示可能範囲をそれぞれ記録する。

## 作業開始時の手順

1. GitHub mainのこの計画とAGENTS.mdを取得し、main・関連ブランチのHEAD、PRの依存関係、CI結果、直近の変更、未コミット変更を確認する。
2. 下の状態表は更新時点の記録なので、APIやgitで現在の状態を再確認する。未完了CIの終了、別担当者の変更、追加コミットを取り込む。
3. 最優先課題を1つ選び、今回の目的と完了条件を短く説明する。新しい工程に依存する未統合コードを読み違えない。
4. 必要ならブランチ/作業領域を分け、既存のユーザー変更を上書きしない。試験的な学習方式は比較し、改善未確認なら採用しない。
5. 実装後に関連テストと既存回帰テストを実行し、数値の変更は独立評価・再現性・統計誤差を確認する。ローカル未実行とCI成功を混同しない。
6. GitHubへ反映し、PR・コミット・CIを照合する。通常のmain統合を行う場合も、依存PR、最新HEAD、CI、レビュー/保護ルール、既存の公開手順を確認して進める。pushだけでmain統合や本番公開を済ませたと報告しない。
7. この計画に結果と次の候補を記録する。1工程の完了で止め、次の独立した工程は次の合図で開始する。

## 精度に関する不変条件

- 未検証・未収束の戦略は「参考戦略」「未確認」と表示し、GTO/検証済みへ昇格させない。
- 既存の認定閾値と認定に必要な根拠を緩めない。学習回数やRegret減少だけではNash収束の証明にならない。
- 固定した近似逸脱候補の改善幅は、厳密BRや真のExploitability上限ではない。多人数ゲームに2人零和のNashConv/2を流用しない。
- 低い改善幅、負の候補成績、候補不採用による0を、均衡の証拠として扱わない。
- 学習・応答探索・選択・最終評価の系列を分離する。独立seedだけでは真のIIDの証明にならないことと、区間の適用範囲を明記する。
- 人数、全員のスタック、ブラインド、アンティ、効用、レーキ、ICM、ゲーム木・履歴・ボード情報の条件を照合する。条件違いの表を流用しない。
- 未学習・未対応をFold/0%や隣のハンドから補完しない。表示した確率の合計、カード除外、精算、サイドポット、保存/再開の再現性を維持する。
- 配札前の位置別EV、ハンド別EV、履歴条件付きEVを区別する。未計算のEVを推測で出さない。

### v1.4での重要な判断

LCFR候補は2学習seedで均等重みより改善を確認できず、初期方式は均等重みを維持。100万回時の平均戦略変化は旧方式約21.5〜21.7pt、候補約29.5pt。最適化kernelの1万反復は中央値1494→1141ms（その環境で約24%短縮）で、元の均等重み戦略と一致。速度向上を精度向上と呼ばない。

## 次の1工程：P0 v1.5の受入・統合整理

**目的：最新の実装・main・実際の配布状態の隔たりを整理し、未統合PRを増やし続けない。**

開始時にPR #1→#2→#3の現在のHEAD・差分・CI・依存関係を再確認する。競合や回帰があればこの工程で修正し、既存ルールに従って統合を進める。保護/レビュー要件などで統合できない場合は、具体的な未完了項目を記録する。main統合後は、実配布先・リリース版・更新ボタンで到達する版を確認する。配布先が未設定なら、設定済みと推測しない。

完了条件：

- 受入対象のコードと成功CIのSHAが一致し、依存関係・統合先・未完了の処理が明確。
- 通常の30BB、10BB学習参考、条件不一致時の非表示、データ破損/旧版、保存再開、更新/PWAの回帰確認がある。
- 計画に「実装済み」「main統合済み」「利用者向け公開済み」を分けて記録。
- この工程では新しい通常Raise/ポストフロップゲーム木や有償大規模計算を追加しない。
