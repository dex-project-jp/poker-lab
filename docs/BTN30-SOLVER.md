# BTN・SB・BB 30BB：実計算と検証

## 到達点と表示範囲

**通常の9人卓MTTのBTNレンジは未完成です。** 今回実装したのは、3人全員の
戦略を同時に探索し、独立した最適反応で検査できる有限の小規模ゲームです。
アプリの「BTN・SB・BB 検証モデル（制約あり）」にのみ結果を表示します。
通常MTTのデータ登録先には入れません。初期画面は引き続き9人・30BBで、
今回の優先ポジションに合わせてBTNを選択します。

## 最終的に解く通常ゲームの条件

- 9人、全員30BB（ブラインド・アンティを支払う前）。UTG〜COがフォールドしてBTN。
- SB 0.5BB、BB 1BB、BBアンティ1BB。開始ポット2.5BB。Chip EV、レーキ0、ICM/バウンティなし。
- BTN Fold / Raise-to-2BB / All-in。SB・BBはFold / Call / 3betなどで応答。
- SB/BBのコール・3bet・4bet・スクイーズ・複数人参加、BTNの再応答、
  フロップ〜リバーの行動・公開カードを含めて一つのゲームとして解く必要がある。
- レイズサイズの候補集合を明記した近似ゲームと、全サイズを許すNLHEを区別する。
- 前の6人のフォールドがカード分布へ与える影響（bunching）も、扱うか省略するか明示する。

## 今回厳密に定義した有限モデル

| 項目 | 条件 |
|---|---|
| 参加者 | BTN / SB / BBの3者。前の6人は強制フォールド、カード・bunchingを省略 |
| スタック・強制ベット | 全員30BB、SB0.5、BB1＋BBアンティ1。BBのライブベット上限は29BB |
| 私有ハンド | AA / KK / QQ / JJから異なる3種類を順序付きで均等配布。各ペアの6スート組み合わせは独立・均等 |
| 公開ボード | **2c 3d 4h 8c 9dを開始時から既知**とする。未知のボード抽選はない |
| BTN初手 | Fold / Raise-to-2 / All-in-to-30。オープンリンプなし |
| BTNがFold | SB Fold / Complete-to-1 / Raise-to-2.5 / All-in。BBはチェック・応答・レイズ |
| 通常レイズ | SBの最初のオープンは2.5、BBの対リンプは3、次のレイズは合計7BB |
| リレイズ | オールインも含め、ベット額の引き上げは最大2回。**4betは許可しない** |
| SB/BBの応答 | Fold / Call / 上記の許可されたレイズ / All-in。BTNも3betにFold / Call |
| 複数人 | 3人参加を含める。短いBBのコール、サイドポット、未コール分の返却を会計 |
| ポストフロップ | ベットなし。プリフロップ終了後すぐ、既知ボードでショーダウン |
| 評価 | ハンド開始前に対する純増減、BB/配られた1ハンド。3人の利得合計は常に0 |

AAなどのセルは、この限定配布内の全6スート組み合わせです。AKsなど他の165セルは
配布されないため、0%ではなく対象外です。このハンド分布は通常の52枚ランダム配布と異なります。
既知の固定ボードがあるため、通常のプリフロップへの助言には使えません。

### スートをまとめられる証拠

24のペアランク配布 × 6³ = 5,184の合法な私有カード配布を全列挙します。
全配布で重複カードを除外し、各ペアの6通りの7枚評価が同一であることを検査。
別のペアランクのスートは独立で、どのスートも利得や他者のランクの情報を変えないため、
この限定モデルでは24ランク配布への縮約が厳密です。未知ボードの通常ゲームには流用しません。

### アンティとサイドポット

アンティ1BBはデッドマネーであり、BBのライブコール額に足しません。
BTN30 / SB30 / BB29のライブベットでは、メインポットは29×3＋1=88BB、
BTN/SBのみのサイドポットは2BBです。BBがAAならメインを勝てても、2BBの
サイドポットを取れません。BTN30対BB29だけなら、BTNの余剰1BBを返却します。

## ソルバーと検証

- ゲーム木：24ランク配布、1,848ノード、124情報集合。相手のカードは情報集合キーに含めない。
- 探索：3者同時CFR+と線形平均。反復数だけで均衡と認定しない。
- 平均戦略と現戦略を実測して最良の候補を保存。検索停止基準は各人の最適応答による
  改善が最大1e-5 BB/hand以下。**ε近似均衡**であり誤差ゼロのナッシュ解とは呼ばない。
- JS検証：相手の戦略を固定し、情報集合を尊重した動的計画法で各人の最適応答を計算。
- 独立検証：Python/SciPy HiGHSで各人のsequence-form最適応答LPを解く。
  JSの最適応答コードを呼ばず、実現確率の制約と終端利得から別に最大化。
- 会計の独立検査：Pythonは0.5BB刻みのチップ断面を使って全1,104終端を再会計。
- 役評価の独立検査：Pythonの5枚組全探索（7枚から21組）とJSの評価器を照合。
- 有理数検査：JSONの十進数を情報集合ごとに正確に正規化した戦略について、Python Fractionで全最適応答を再計算。改善上限が1/100,000 BB以下であることを整数の分子・分母で比較します。浮動小数点の丸めだけで基準を通しません。
- 公開ゲート：候補・ゲーム木のSHA256、全3者のε、独立LPとの差、5,184配布の検査を確認。
  基準未達や入力不一致なら検証モデルの頻度も表示しない。

最適応答の利得を `g_i = BR_i(σ_-i) - u_i(σ)` とし、`ε=max_i g_i` を使います。
NashConvは`Σ_i g_i`。HUのgap/2を3人ゲームの攻略可能性として流用しません。
基準を満たす候補が見つかったという実測で、CFR一般の3者ナッシュ収束定理ではありません。

計算記録：[btn-mini-validation.json](../solver/data/btn-mini-validation.json)。
今回の探索は61.2万反復・約103秒、独立したLP検査は3本。
数値は浮動小数点であり、JS/LP照合許容差は1e-9 BBです。全メモリ使用量は未計測。
通常30BB NLHEの計算時間・RAM要件を、この小規模実測から推測しません。

## 再実行

```sh
cd solver
npm run solve:btn-mini      # 候補を探索。未検証として保存
npm run export:btn-mini     # 有限ゲーム木を再生成
npm run check:btn-mini      # Pythonの独立LP・役・カード・会計を照合
npm run certify:btn-mini    # 基準を通った小規模モデルだけを生成
npm test
```

CIは探索をやり直す代わりに、保存候補に対して最適反応とLPを再計算します。
候補を生成したアルゴリズムに依存せず、その候補の近似均衡性を検査できるためです。

## 再利用と新規実装の境界

- 再利用：実カード評価器、重複検査、Chip EVの単位・入力検証、HU回帰テスト、169表の描画。
- 新規：3者ベット木、情報集合、デッドアンティ/サイドポット、3者のCFR探索と最適反応、独立LP。
- 再利用しない：HUの169×169勝率表で3者ショーダウンを近似すること、HUの均衡証明、HUのスタック条件照合。

## 次の拡張と調査

1. 制限ゲームを保ったまま手札種類と未知ボードを増やし、全列挙できる範囲で検証を続ける。
2. 4bet/追加サイズとポストフロップの行動をゲーム木に加え、各段階で利得・最適応答を照合する。
3. 全52枚のBTN/SB/BBへ拡張。3者の私有カードとボードを素朴に全列挙すると
   C(52,2)C(50,2)C(48,2)C(46,5)もの確率事象があり、今回の方式をそのまま全探索しない。
   MCCFR、スート対称性、カード/行動抽象化、並列実装を調査し、抽象化誤差と検証範囲を明示する。
4. 前の6人のフォールド条件とbunchingを取り込み、9人卓のBTN条件へ接続する。
