# v1.1：通常デッキ・未知ボードへの拡張

**実戦用9人卓GTOは未計算です。** v1.0の特殊な配札・既知ボードの戦略は維持し、新しい通常デッキ計算に流用しません。v1.1は配札、未知ボードの勝敗、精算の検証を優先した段階です。新しい戦略頻度を169表に公開していません。

## 実装した範囲

`solver/mtt10-deck.js` は52枚、全1,326非順序ホールカードコンボ、169クラスを登録。ペア6、suited4、offsuit12の内訳を全クラス検査します。各席の実カード2枚を維持し、169クラスだけを独立抽選する方式ではありません。

9人に18枚を配り、**Fold済みの私札も取り除いた残り34枚**から5枚のボードを非復元抽選します。既知の手札を指定した条件付き抽選、検証用の部分ボードにも対応します。既定ではボードは空で、未知です。任意の9人の手札・ボード23枚の重複を検査します。

部分Fisher–Yatesを使い、整数乱数はrejection samplingで剰余バイアスを避けます。疑似乱数は再現可能なMulberry32と32-bit seed。理想的に独立一様な乱数が入力されるなら合法な残りカードを一様抽選しますが、有限状態PRNGが真のIIDや全配札空間の一様性を数学的に保証するとは主張しません。独立検証器は別のPython整数実装とremove-by-swap抽選で同じ標本を再現します。これは実装照合であり、独立した乱数系列による再実験ではありません。

勝敗は7枚評価器で最大9人を同時比較。同点持分と、ポット層別の精算を分けます。エクイティは全アクティブハンド間で最高順位となった持分であり、サイドポットの参加資格を反映した獲得チップ率ではありません。利得は各ポットの参加資格、同点、未コール返却、デッドアンティを適用して別に計算します。`awards`は返却を含む総受取、`refunds`はその内訳なので二重加算しません。

## 共通の計算条件

9人・全員の強制ベット前スタック10BB。SB 0.5BB、BB 1BB、BBアンティ1BB。Chip EV、ICM・レーキ・バウンティなし。BBの残りスタック8BB、ライブ投入上限9BB。他席はライブ上限10BB、SBの残り9.5BBです。

全員All-inならライブ89BB＋アンティ1BB＝90BB。全員が争う主層は82BB、BBを除く8人のサイド層は8BB。例えばUTG Jam10BBにBBだけがCallすると、強制ベットを含む総投入20.5BB、UTGへ1BB返却、争う額19.5BBとなります。

## 実行したサンプリング

| 条件 | seed | 標本 | 内容 |
| --- | --- | --- | --- |
| all-nine-random | 110101 | 20,000 | 9人全員ランダムなホールカードで参加 |
| utg-AA-vs-BB-random | 110102 | 20,000 | UTGのAsAh固定、BBランダム、他7人はFold |
| AA-overcall-three-way | 110103 | 20,000 | UTGのAsAh固定、UTG+1とBBがランダム参加、他6人Fold |

参加・Foldはカードとは独立に固定しています。**実際のFoldやCallが示すレンジによる条件付け・カードバンチング推定は未対応**です。Foldした私札そのものの除外と、アクションからその分布を推測することは別です。相手ランダムに対する勝率から最適Call等を推奨しません。

全員ランダムの標本では169クラス／1,326コンボを観測。AsAh固定時は、他席にAs/Ahを含む100コンボを配れないため、全席合計で観測できるコンボは1,226（固定AsAhを含む）。これは手札クラス別・席別の十分な標本数や戦略の計算完了を意味しません。

各条件のエクイティは[0,1]の標本平均。9人の平均値に対してunion boundを使うHoeffding半幅は `sqrt(log(18/alpha)/(2N))`、alpha=.05、N=20,000で **0.01213064717（約1.2131ポイント）**。理想IID仮定の同時95%区間です。区間は条件ごとで、3条件全てやエクイティ・利得の全指標を一緒に95%保証する意味ではありません。標準誤差も別途記録します。利得は各席の[-投入額, 総投入−投入額]という有界区間を使い、別の同時区間を保存しています。この幅は数値実装の誤差やGTOの誤差ではありません。

## 独立検証と参照比較

`tools/check-mtt10-deck.py` は全60,000配札を独立に再生成し、毎回9人の7枚から21通りの5枚部分集合を評価。別実装の0.5BBスライスで全員の利得・返却を精算し、JS出力と照合します。許容差はエクイティ1e-12、平均利得1e-10BB。実測差は `mtt10-deck-independent.json` に保存。

追加の独立した基準：

- 全員ランダムのショーダウン持分の厳密期待値は対称性から各人1/9。9人とも表示区間内であることを確認。
- 既存の厳密HUカード除外・全ボード列挙行列から、AA対ランダムのエクイティを合法コンボ重みで集計。**85.2037133021%**。今回の標本推定 **85.3425%**、差 **0.1387867ポイント**で、表示区間内。固定参加で他7人のランダム私札を周辺化すればHUと同じ分布になるため、この条件に限り比較できます。HU勝率をマルチウェイ勝率に変換してはいません。
- 全18私札とturnまでの4枚を固定する別ケースで、合法なriver30枚を全列挙し、別seedの10,000標本との一致を区間で確認。
- ロイヤルフラッシュの共有ボードで9人同点、主層・サイド層の異なる分配、HU返却1BB、全状態のチップ保存を検査。

入力ソース、候補、有限木、独立検証結果をハッシュで結び、照合に成功した場合だけブラウザ用の検証レポートを書き出します。第三者の有料データ・レンジ・頻度は使用していません。HU比較は既存リポジトリの計算データです。

## 多人数CFR+への接続試験

既存の `multiplayer-solver.js` を改変せず、`buildSampledGame` から通常デッキ配札と未知ボードを含む有限経験分布を供給します。アクションは既存のFold/Jam/Call・オーバーコール。情報集合のキーは **自分の実コンボ＋公開履歴＋席**であり、ボード・他人の札・チケット番号を含みません。

16標本（seed110104）、16,336ノード、各自1回行動。上限200反復・20反復ごとに計測し、今回20反復で訓練標本内の最大改善幅0BBになりました。これは**通常デッキのNash収束ではありません**。各席の16個の私札コンボがいずれも異なるので、有限の訓練分布では私札から配札チケットとボードを推測でき、深刻な過学習が起きます。少数の事前抽選を固定してεが0になるだけでは実戦の保証にならないことを確認する診断です。

独立検証器はこの木の8,176終端のポットを再評価し、各情報集合の2アクションの係数を集計して全9人の最適応答を別計算。比較するのはこの有限経験ゲームだけです。未知の通常配札全体に対する最適応答、holdoutでの改善幅上限は未検証。頻度は再現用候補ファイルに保存しますが、ブラウザ用レポートからpolicy配列を除き、レンジ表には一切反映しません。

実行時間・最大RSS・反復履歴・席別の私札重複数はレポートに記録。初回JSの3条件サンプリング＋探索は約2.03秒、peak RSS約153.6MiB（Node24、Linux、機器依存）。独立Pythonの全5枚部分集合評価はこれとは別の追加時間です。

[Lanctot et al., Monte Carlo Sampling for Regret Minimization in Extensive Games (2009)](https://proceedings.neurips.cc/paper/2009/hash/00411460f7c92d2124a67ea0f4cb5f85-Abstract.html) を次のchance-sampled CFR/MCCFR実装の検討資料とします。今回の『固定された16配札をCFR+で解く』処理を、本来のfresh-chance MCCFRと呼びません。**多人数でCFR+から完全なNash収束保証を無条件に得ることはできません。** v1.0で述べたHU minimaxの保証も転用しません。文献は手法の参考であり、レンジデータ・コードの転載ではありません。

## アプリと再現方法

設定 → 『v1.1 通常デッキ・未知ボードの検証結果』で、固定参加の推定エクイティ・区間・標本数を表示。推奨アクションやEV・戦略頻度は表示しません。データが欠落・不整合の場合は数値を隠して未計算とします。30BB参考表、HU5〜20BB、v1.0制限実験、3者モデル、段階式UIと更新ボタンはそのまま維持。

```sh
npm test --prefix solver
npm run sample:mtt10-deck --prefix solver  # 再抽選・候補再計算、実測資源が変わる
npm run export:mtt10-deck --prefix solver
npm run check:mtt10-deck --prefix solver   # 独立結果を書き出す
npm run certify:mtt10-deck --prefix solver
# 保存済み候補のCI照合は check:mtt10-deck -- --check
npm run test:browser --prefix solver
POKER_BROWSER=webkit npm run test:browser --prefix solver
```

通常のCIは保存済み候補の60,000標本を再評価し、出力の再現性を確認します。PRNG標本の再現とモンテカルロ近似の正確さは別の検証項目です。

## 次の課題

1. 新しい配札・未知ボードを反復ごとに抽選するCFR/MCCFRを実装し、情報集合の再利用と稀なコンボへの標本配分を設計。カード除外を維持しつつ、計算量を削減する。
2. 学習に使わない複数seedの配札で評価し、各人の最適応答の推定、標準誤差・信頼上限を導入。訓練内εと通常デッキでの攻略可能性を明確に分離。
3. 参加者の戦略とFold履歴から条件付き配札分布を扱う。169クラスへの集約を行うなら、その抽象化誤差も検証する。
4. 通常Open/Limp/3bet/4betを含む複数回行動の木、sequence-form BR、さらに異スタック・ICMへ拡張。

今回、通常9人10BBの169ハンド戦略・実戦GTOは完成していません。有料サービスは使用していません。
