## 初期の計算予定条件

| 条件 | 定義 |
|---|---|
| 人数 | 9人、NLHE、MTT |
| ポジション | UTG、UTG+1、UTG+2、LJ、HJ、CO、BTN、SB、BB |
| スタック | 全員30BB、ブラインドとアンティを支払う前 |
| ブラインド | SB 0.5BB / BB 1BB |
| アンティ | BBが1BBを負担。開始ポット2.5BB |
| 評価 | Chip EV、レーキ0、ICMなし、バウンティなし |
| オープン | UTG〜BTNは合計2BBへレイズ、SBは合計2.5BBへレイズ |
| リンプ | SBのみ合計1BBへのコンプリートを許可 |
| 初期対象 | UTG〜SBの8オープンノード（前の全員がフォールド） |
| BB | 前の8人全員がフォールドしたらウォーク。オープン対象外 |

上記のサイズは**計算予定のゲーム定義**であり最適サイズの計算結果ではありません。
通常レイズ後のコール・3bet・4bet、複数人参加、フロップ以降を含むゲームで
戦略を検証する必要があります。オープン時の選択肢だけを計算して、その後の
全ハンドがショーダウンに進むと仮定する近似はGTOとして公開しません。
SBのCallはリンプに相当します。BBウォークをCheck 100%とは表記しません。

## 10〜100BBへの拡張

初期選択30BB。10〜100BBを1BB刻みで選択でき、未登録は「未対応」。
30BBの上記条件は「検証待ち」。30BBでも条件を変えると「未対応」です。
9人全員のスタックが照合対象で、HU用のmin(Hero,Villain)は流用しません。

## 検証済みデータを導入する手順

1. 指定ゲームの戦略と、元ソルバーのバージョン・完全なベットツリーを確保する。
2. 商用アプリへの再配布可否を確認する（無料閲覧と再配布の許可は別）。
3. 169クラス全頻度、1,326コンボの重み、全プレイヤーの除外・配布条件を確認。
4. 全ゲームにおける各プレイヤーの一方的な戦略変更による利得の上界を、
   配られた1ハンド当たりBBで検証。抽象化の誤差も含める。
   HUのNash gapを9人の均衡証明に流用しない。
5. 別の計算結果との照合、ブラインド・アンティ・全員のスタックの照合。
6. 証拠ファイルを含むbundleを tools/check-mtt-bundle.mjs で構造を検査する。
   このコマンドは数学的な検証・インポート・公開を行いません。

`mtt-model.js`のinspectは証拠メタデータの**必要条件を検査するゲート**です。
文字列のハッシュやverified=trueだけで、計算そのものの正しさを証明しません。
独立した証拠の実査・数値検証は別に必要です。

今のHUソルバーは二者・二択用で、9人30BB通常オープンを解く機能はありません。
次の実計算には、多人数・複数ベットサイズ・ポストフロップを扱うソルバーの
実装または再利用できる検証済みデータが必要です。
